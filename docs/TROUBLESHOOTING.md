# 排障记录

## 1. agent 模式发“你好”要等几十秒到几分钟，最后没显示（已定位）

**现象**：Trae / ZCode 的 agent 模式下发一句“你好”，等 67 秒甚至几分钟没回、
界面没字也没报错；同样的服务，curl 发 14 token 的小请求 0.38 秒首 token、
0.57–0.72 秒回完。

**原因**：agent 模式发过去的根本不是一句“你好”，而是系统提示 + 一堆工具定义 +
对话历史，实际有几万个 token。证据：

- 2026-11-10：ZCode 一次发了 32769 个 token，刚好超过当时 32768 的上限 1 个；
  之前一次是 16385 超过 16384 上限 1 个——每次都是刚好超 1 个，
  说明是客户端把窗口塞满了再发，不是多打了一句话。
- 2026-11-11 10:50：ZCode 截图显示供应商耗时 67 秒、读取返回 67 秒，
  `the agent canceled the request`——客户端等不到首个 token 自己取消了。
- 服务端侧每次都正常：请求到了、HTTP 200、GPU 算完空闲、无 OOM、无报错，
  流式测试也正常。

**为什么这么慢**：T4 是 Turing 架构，不支持 FlashAttention 2，
vLLM 必须加 `--enforce-eager`（不用 CUDA graphs），
几万 token 的 prefill 在 T4 x2 上要算几十秒到几分钟。

**怎么办**：

1. 日常写代码用 **chat 模式**（普通聊天，不带 agent 工具），
   2026-11-11 11:23 已验证可用，写了脚本，只是速度慢。
2. 必须用 agent 模式时：新开对话、只挂这次要改的几个文件，
   别把整个仓库和长历史都带上。
3. 不要靠一味抬高 `max_model_len` 解决：65536 已经是两张 T4 显存的上限附近，
   再往上提会 OOM；而且提上限只会让客户端塞进更大的提示，更慢。

## 2. ZCode 里上下文窗口还是 32768，服务端已经是 65536

ZCode 会按它自己设置的上下文窗口数来打包历史和工具定义。
把 ZCode 设置里的上下文窗口从 32768 改成 65536，保存，再**新开对话**发。
（只改数字不新开对话没用，旧对话的历史还在按旧窗口算。）

## 3. Kaggle 编辑器一直显示 Failed to save draft

2026-11-10 遇到：改 QuantTrio 的编辑没保存到服务器，刷新可能恢复成旧的
Qwen 仓库名；重试仍失败（`ConcurrencyViolation`，服务端草稿序号 16、
当前编辑器序号 9）。原因不是双开，是服务端序号冲突。
**做法**：以本地这份 notebook 为准（`notebooks/` 下的就是已修正版），
每次重跑直接新导入一份，别在 Kaggle 编辑器里改了指望它保存。

另外跑之前先看一眼第 3 个 cell：仓库名必须是
`QuantTrio/Qwen3-Coder-30B-A3B-Instruct-AWQ`，要是还是
`Qwen/Qwen3-Coder-30B-A3B-Instruct-AWQ` 就别跑，会报 401
（Qwen 官方根本没发过 AWQ 版）。

## 4. 浏览器直接打开隧道地址被 Cloudflare 拦截

2026-11-11：本机浏览器两次打开新隧道都显示 blocked，但 curl / urllib 正常。
API 客户端（Trae / ZCode）走的是 HTTP 调用，一般不受影响；
如果客户端也被拦，重启 cloudflared 换个新地址即可。

## 5. 旧隧道地址突然不通了

会话结束隧道即失效，地址作废。下次重跑要换新地址，
记得同步改 Trae / ZCode 里的 Base URL（旧地址不会自动跳转）。

## 6. 想给隧道加鉴权（可选，未实测）

现在 vLLM 没设 Key，隧道地址谁拿到都能免费用，并行只有 2 个，
别人占了你的请求就得排队。加固两步：

1. 重启 cloudflared 换新隧道地址，旧地址立刻失效；
2. 启动 vLLM 时加 `--api-key <只有你知道的串>`，
   Trae / ZCode 里把 API Key 填成同一个串。

已纠正：隧道未证实被他人占用，加固不紧急。
